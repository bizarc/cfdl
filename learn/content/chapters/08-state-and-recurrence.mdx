Everything you have computed so far is *memoryless*: an amount at period 12 reads the clock, the assumptions, a curve — but never period 11's answer. A loan balance cannot be written that way, and neither can a compounding index off a varying rate, a cumulative-spend tracker, or an escalation that rounds before it compounds. These are **recurrences** — this period's value defined in terms of last period's — and `state` is the construct that carries them.

## init and next

```cfdl
version 0.1
model "state-index"
time calendar annual from 2026-01 for 5

entity asset co : Asset.Financial

// A growth rate that decays from 5% to 3% over the horizon.
curve growth linear {
  2026-01: 0.05
  2030-01: 0.03
}

// An index that compounds whatever rate prevails each year. This is the
// claim pow() cannot make: pow applies ONE rate as though it had held from
// the start, and this rate changes.
state revenue_index {
  init 1.0
  next prev * (1 + curve_value("growth", time.date))
}

stream co.revenue on entity asset.co inflow currency USD {
  schedule every year from 2026-01 to 2030-01
  amount = 1000000 * state.revenue_index
}

stream co.overhead on entity asset.co outflow currency USD {
  schedule every year from 2026-01 to 2030-01
  amount = 650000
}
```

A state has exactly two clauses. **`init`** is the value at the first period. **`next`** is the recurrence — evaluated each subsequent period, with **`prev`** bound to this state's own value one period ago. Streams read the current value as `state.<name>`.

The two archetypes cover most of practice: **multiplicative** (`prev * (1 + rate)` — indexes, balances accruing interest, anything compounding) and **additive** (`prev + amount` — cumulative spend, units sold to date, anything counting). The example is multiplicative with a twist that justifies the whole construct: the rate *varies*, so each year's growth must apply to the *already-grown* value. `pow(1 + g, t)` cannot say that; a recurrence says exactly that.

## Why cycles are impossible

Here is the design decision that makes state safe to use freely. A `next` expression can read `prev`, other states' previous values (`prev.other_index`), the clock, assumptions, and curves — everything from the *completed* previous column. It cannot read any same-period value: not another state's current value, not a stream's current amount, not its own.

The consequence: circular references — the spreadsheet's most notorious failure mode — are not detected and warned about; they are **unwritable**. Two states may reference each other freely, because each reads the other's *previous* value, and last period is always finished. Declaration order carries no meaning. The iterative-solver dance ("enable circular references, set max iterations…") that infects interest-on-average-balance spreadsheet models has no equivalent here, because the language grammar itself is the proof that evaluation is well-founded.

The cost of that guarantee is one modeling discipline: same-period simultaneity must be *staged*. Interest on the average of opening and closing balance — a genuinely simultaneous definition — becomes interest on the *opening* balance (that is, `prev`), or a two-state formulation, and either way the model states its convention explicitly. That is the trade throughout this language: a construct that cannot express confusion, in exchange for saying what you mean.

## The rounded-escalation case

The canonical case for state over formula, promised in chapter 3. A published schedule escalates a fee 3% annually, *rounding to the dollar each year* — and compounds next year on the rounded value, because that is what the spreadsheet it came from did:

```cfdl
version 0.1
model "state-rounded-escalation"
time calendar annual from 2026-01 for 6

entity asset co : Asset.Financial

// Escalate, round to the dollar, and NEXT year compounds on the ROUNDED
// value — the recurrence a clean pow() formula cannot reproduce.
state fee_schedule {
  init 100000
  next round_to(prev * 1.03, 1)
}

stream co.management_fee on entity asset.co inflow currency USD {
  schedule every year from 2026-01 to 2031-01
  amount = state.fee_schedule
}

stream co.admin_cost on entity asset.co outflow currency USD {
  schedule every year from 2026-01 to 2031-01
  amount = 20000
}
```

Over six years, `100000 * pow(1.03, time.t)` and this recurrence drift apart by about a dollar — and over the thirty-year schedules where this pattern actually lives, by real money. Invisible in a total, fatal in a reconciliation that must match a source to the penny. The state version matches the *method*, so it matches the pennies, and every future deviation from the published schedule is a visible choice rather than an unexplained residual. This pattern — carry the rounded value forward — is the single most common reason mature models need state at all.

## A state's clock is its own

By default a recurrence steps once per model period, over the whole timeline. But a state can carry its own schedule, exactly as a stream does:

```cfdl
// Steps once a quarter, whatever the model's grain.
state quarterly_index {
  schedule every quarter from 2026-01 to 2027-12
  init 1.0
  next prev * (1 + inputs.quarterly_rate)
}
```

This matters the moment grains mix. A pool that accrues on a monthly book inside a daily-grain model must *not* compound its monthly hazard 365 times a year — that is not a rounding error, it is a different number entirely. The state's own schedule pins the recurrence to the cadence the claim is actually made at, and the model's grid stays free to be as fine as the finest cash.

## What state is not

State is **not cash**. A balance, an index, a counter — none of them appear in results as flows; they are the model's working memory, and only streams that *read* them produce cash. If you find yourself wanting a state's value to "land" somewhere, what you want is a stream whose amount reads the state.

And state is not the answer to everything sequenced. When the thing that accumulates is *someone's entitlement* — arrears owed, a preferred return accruing until paid — the language has purpose-built constructs (`waterfall`'s `owed` and `paid`, chapter 11) that carry the entitlement *and* the payment against it together. Reaching for raw state there means hand-building what the waterfall already proves correct. Part III's construct-choice chapter draws this line precisely; for now, the smell to notice is a state paired with a stream that tries to "pay it down."

## What can go wrong

**Reading a current value that does not exist yet.** Write `next` in terms of another state's *current* value and the expression is refused — the environment simply has no such name. The error is the design working.

**An `init` that contradicts the first payment.** The classic off-by-one: does the balance start at the principal, or at the principal less the first payment? `init` is the value *at the first period, before any `next` has run* — anchor it to a dated fact (the closing balance on day one) and hand-check period 0 and period 1, once, every time you write a balance.

**A recurrence at the wrong cadence.** A monthly rate in an annual `next`, or the reverse — the engine cannot know a number's intended cadence. The defense is the state-schedule feature plus the chapter-3 habit: one hand-checked step.
